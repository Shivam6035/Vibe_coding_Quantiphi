PART 1: THE IDEA, THOUGHT PROCESS & HOW WE BUILT IT (YOUR OPENING PITCH)
--------------------------------------------------------------------------------
If the evaluator opens with: "Walk me through your approach and how you built this,"
use this structured 4-step narrative:

1. THE CORE IDEA & ARCHITECTURAL PHILOSOPHY:
   - Given the strict requirement that ALL business logic, validations, and
     calculations must reside on the server side while the frontend handles only
     presentation and user interactions, I designed a strictly decoupled
     3-tier architecture:
       (a) Presentation Layer: Vanilla JS + Tailwind CSS + Chart.js (Zero math).
       (b) API & Validation Layer: FastAPI + Pydantic v2 (Input sanitization).
       (c) Service & Persistence Layer: Async HTTPX + SQLite3 (Caching & state).
   - I intentionally avoided heavy frontend build tools (like Webpack/Vite/React)
     and served static HTML/JS directly via FastAPI so I could focus 100% of the
     90-minute window on backend robustness, clean API contracts, and edge-case
     handling.

2. STEP-BY-STEP BUILD EXECUTION:
   - Step 1 (Data & Persistence Layer - `app/database.py`):
     Before touching the API, I designed the SQLite schema with 3 tables:
     `favorites` (with a UNIQUE constraint on source & target currency),
     `conversion_history` (to log conversions), and `rate_cache` (a TTL cache
     table to prevent external API rate-limiting).
   - Step 2 (Validation Contract - `app/schemas.py`):
     I used Pydantic v2 models (`ConvertRequest`, `TravelBudgetRequest`) with
     custom `@field_validator` methods to enforce that currency codes are valid
     3-letter alphabetical ISO strings and amounts are strictly greater than 0
     (`gt=0`) before any service code runs.
   - Step 3 (Core FX & Business Logic - `app/services/fx_service.py`):
     I built the ExchangeRate API integration using async `httpx`, added the
     30-day time-series aggregation logic (computing min, max, and % change on
     the server), and wrote the "Vibe Check" Travel Budgeting matrix calculator.
   - Step 4 (REST Endpoints & UI Binding - `app/api/routes.py` & `frontend/`):
     I exposed clean REST endpoints (`/api/convert`, `/api/trends`,
     `/api/travel-budget`, `/api/favorites`, `/api/history`) and wired them to
     `frontend/app.js` using async `fetch()` calls.

PART 2: THE 5-POINT TECHNICAL VIVA CHEAT SHEET (MOST LIKELY Q&A)
--------------------------------------------------------------------------------

Q1: "How did you ensure ZERO business logic or validation happens on the frontend?"
--------------------------------------------------------------------------------
- What they are testing: Compliance with the core architectural constraint.
- Your Answer:
  "In `frontend/app.js`, the JavaScript code only reads raw DOM inputs, sends a
   JSON payload via `fetch()`, and injects the returned server strings directly
   into the HTML.
   - Validation: Handled in `app/schemas.py` via Pydantic (`Field(..., gt=0)`
     for positive numbers and `validate_currency_code()` to strip whitespace,
     uppercase, and verify 3-letter ISO format).
   - Conversion Math: Handled in `perform_conversion()` inside `fx_service.py`,
     which computes both `converted_amount = round(amount * rate, 4)` and the
     `inverse_rate = round(1.0 / rate, 6)` on the server.
   - Chart Aggregations: Even the 30-day `min_rate`, `max_rate`, and `pct_change`
     badges shown above the chart are calculated in Python inside
     `get_30_day_trends()`, not in JavaScript."

Q2: "How does your SQLite persistence work, and how do you handle duplicate
     favorites or frequent API calls?"
--------------------------------------------------------------------------------
- What they are testing: Database design, SQL knowledge, and caching strategy.
- Your Answer:
  "I used Python's built-in `sqlite3` module in `app/database.py` with
   `sqlite3.Row` factory so queries return dictionary-compatible rows.
   1. Preventing Duplicate Favorites: In the `favorites` table DDL, I added a
      composite constraint: `UNIQUE(source_currency, target_currency)`. When
      inserting, I use `INSERT OR IGNORE INTO favorites...` so clicking 'Save'
      multiple times on the same pair is completely idempotent and never crashes.
   2. Preventing API Rate-Limiting (Write-Through Cache): I created a `rate_cache`
      table that stores the ExchangeRate API JSON response keyed by
      `base_currency` along with a Unix timestamp (`updated_at`). In
      `get_cached_rates()`, if the cached entry is younger than `CACHE_TTL_SECONDS`
      (900 seconds / 15 minutes), the server serves rates directly from SQLite
      in under 2ms instead of making a redundant external network call."

Q3: "Walk me through 'The Vibe Check' (Travel Budgeting Mode). What happens if
     the user's base currency is already one of the 5 major currencies?"
--------------------------------------------------------------------------------
- What they are testing: Edge-case thinking in `calculate_travel_budget()`.
- Your Answer:
  "When the user toggles Travel Budgeting Mode, the frontend calls
   `POST /api/travel-budget` with `{ base_currency, amount }`.
   - Edge Case Handled: If a user selects `USD` as their base currency, showing
     `USD -> USD` in the 5-currency comparison table would be useless.
   - Solution: In `app/config.py`, I defined a pool of 6 major global currencies
     (`USD`, `EUR`, `GBP`, `JPY`, `AUD`, `CAD`). In `calculate_travel_budget()`,
     I use a list comprehension:
     `target_majors = [c for c in MAJOR_GLOBAL_CURRENCIES if c['code'] != base][:5]`
     This dynamically filters out the user's base currency and slices the top 5
     remaining major currencies, fetching the live rate once (or from SQLite
     cache) and computing all 5 equivalent values simultaneously on the server."

Q4: "How did you implement the 30-day historical trend chart, and what happens
     if the historical API fails or doesn't support a currency?"
--------------------------------------------------------------------------------
- What they are testing: API resilience, fallback patterns, and async I/O.
- Your Answer:
  "Standard free tiers of ExchangeRate-API provide live spot rates (`/v6/latest/{base}`),
   while historical time-series endpoints often restrict exotic currencies or
   require paid keys. To make the 30-day trend chart 100% resilient:
   1. Primary Path: `get_30_day_trends()` first queries the historical time-series
      endpoint (`api.frankfurter.dev`) for the exact 30-day window (`start_date`
      to `end_date`).
   2. Resilient Fallback Path: If the external historical service times out or
      doesn't support a specific currency pair, the backend catches the exception,
      fetches the real live spot rate from ExchangeRate-API, and generates a
      deterministic 30-day series anchored to today's exact live rate (using an
      MD5 hash seed of `src_tgt` so the curve stays consistent across refreshes).
   3. Same-Currency Edge Case: If `source == target` (e.g., USD to USD), it
      immediately returns a flat array of `1.0` with `0.0%` change without wasting
      an API call."

Q5: "Why did you use `async def` with `httpx.AsyncClient` and FastAPI's `lifespan`
     context manager?"
--------------------------------------------------------------------------------
- What they are testing: Senior-level Python/FastAPI concurrency knowledge.
- Your Answer:
  "1. Non-Blocking I/O (`httpx.AsyncClient`): If you use standard synchronous
      `requests.get()` inside an `async def` FastAPI route, it blocks the entire
      Python ASGI event loop while waiting for the external ExchangeRate API.
      Using `async with httpx.AsyncClient(timeout=8.0)` allows Uvicorn to handle
      concurrent requests (like loading `/api/history` and `/api/trends` in
      parallel via `Promise.all` on the frontend) without blocking.
   2. Modern Lifespan Manager: Instead of the deprecated `@app.on_event('startup')`,
      I used FastAPI's modern `@asynccontextmanager async def lifespan(app)` in
      `app/main.py` to guarantee `init_db()` creates the SQLite tables and seeds
      default favorite pairs (`USD/INR`, `EUR/USD`, `GBP/INR`) before the server
      accepts its first request."
